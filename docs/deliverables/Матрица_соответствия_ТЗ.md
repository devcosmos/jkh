## Итоговый продукт (docs/source-data/ТЗ_сайта.md, раздел «Описание итогового продукта»)

Формулировка задачи с сайта: «Разработайте веб сервис, использующий предиктивную ML-модель...
Программный продукт (сервис): предиктивная ML-модель прогнозирования аварий и отказов
оборудования + веб-интерфейс диспетчера ОДС с дашбордом рисков, картой объектов и журналом
прогнозов + модуль автоматического формирования заявок на превентивное обслуживание + REST API».
Все четыре компонента реализованы:

| Компонент | Статус | Реализация |
| --- | --- | --- |
| Предиктивная ML-модель | ✅ | Два независимо обученных `CatBoostClassifier` (по одному на трек «Отказ датчика»: насос/вентилятор и дым/газ — направление прямо названо в ТЗ, строка 17) — реальные train/val/test с разрывом 24ч (`ml/training/train_model*.py`), метрики зафиксированы в `artifacts/model_report_*.md`. В проде инференс живой: `backend/app/workers/replay_worker.py` на каждом тике считает признаки из потока событий и вызывает `model.predict_proba(...)` на загруженном `.cbm`-артефакте. Дополнительно: SHAP-объяснение конкретного прогноза (`explain_prediction`) и независимый сигнал аномальности — `IsolationForest` без учителя на тех же поведенческих признаках (`ml/training/train_anomaly_model.py`), обучен отдельно от CatBoost и способен отметить поведение вне размеченных сценариев отказа. Ещё один доп. сигнал внутри того же направления — тренд частоты эпизодов по каналу (растёт/падает за 90 дней), реализованный 21 сентября (`backend/app/services/degradation_trend.py`, `docs/documentation/Тренд_частоты_эпизодов.md`) — не путать со строкой «Износ инфраструктуры» ниже: это разные вещи, тренд не опирается на возраст/дату установки оборудования |
| Веб-интерфейс диспетчера: дашборд рисков, карта объектов, журнал прогнозов | ✅ | `frontend/src/pages/DashboardPage.tsx` (обзор с показателями), `RisksPage.tsx` (дашборд рисков + схема объектов вместо GPS-карты — по прямой рекомендации организаторов, координат не будет никогда, тема 14 CSV), `JournalPage.tsx` (журнал прогнозов) |
| Модуль автоформирования заявок на превентивное обслуживание | 🟡 | ТЗ называет модуль «автоматическим», фактическая реализация — по явному решению диспетчера «направить на проверку» (`app/services/maintenance_requests.ensure_request_for_dispatch`). Автосоздание черновика worker'ом по одному порогу вероятности существовало раньше и было сознательно убрано по решению заказчика (см. докстринг `app/services/maintenance_requests.py`) — риск-кейс выше порога сам по себе не признан достаточным основанием для заявки без решения человека. Формирование заявки (шаблон вида работ, дедуп, полный жизненный цикл `draft→approved→in_progress→completed`) реализовано полностью, но запускается диспетчером, не автоматическим правилом — метка понижена до частичного соответствия честно, не потому что чего-то не хватает технически. Полный жизненный цикл — `frontend/src/features/requests/RequestsPage.tsx` |
| REST API | ✅ | FastAPI, `backend/app/api/*`, автогенерируемая OpenAPI-схема |

Целевые метрики раздела («Precision > 0.7 и Recall > 0.5», горизонт ≥24ч, инференс <5 мин) —
см. раздел 9 ниже: целевое окно реализовано, время требует проверки под нагрузкой, Precision/Recall — плановая, не
жёсткая цель (тема 3 CSV), рабочая точка выбрана по эпизодной оценке и честно задокументирована.

**О четырёх направлениях прогнозирования (строки 17-20 `ТЗ_сайта.md`):** команда сознательно
сосредоточилась на «Отказ датчика» (строка 22 разрешает выбрать одно или несколько
направлений). Трек дым/газ прогнозирует неисправные состояния каналов. Наличие этих датчиков в признаках не подтверждает прогнозирование пожара; отдельная модель пожарного риска не реализована. «Несанкционированный доступ» и «Износ
инфраструктуры» не реализованы — данные СКУД/журналов допусков и визуальных обследований
организаторами не предоставлены.

## Раздел 9. Производительность и качество прогнозирования

| Требование | Статус | Реализация / обоснование |
| --- | --- | --- |
| Inference ≤ 5 минут на объект | 🟡 | В исторических наблюдениях тик занимал секунды. Полная задержка при целевой нагрузке отдельно не измерена — [протокол](../documentation/Протокол_проверок.md) |
| Precision/Recall — «определяются на этапе проектирования исходя из качества данных» (раздел 9 ЖКХ.md) | 🟡 | Целевые Precision>0.7/Recall>0.5 из `ТЗ_сайта.md` не достигнуты ни для насос/вентилятор (`artifacts/model_report_насос_вентилятор.md`), ни для дым/газ (`model_report_дым_газ.md`). Тема 3 CSV подтверждает: «указанные значения являются плановыми, а не жёсткими требованиями… если данные не позволяют достичь этих уровней, их можно снизить, обязательно обосновав». Обоснование: сигнал в данных (история состояний самого канала) статистически слаб — ROC-AUC 0.71/0.63 против случайных 0.5, но PR-AUC на два порядка ниже требуемой точности; три проверенные гипотезы улучшения (соседние устройства, дневная гранулярность, числовые каналы) не дали качественного прорыва. Рабочая точка порога выбрана по эпизодной оценке (`ml/evaluation/evaluate_episodes*.py`), а не по «жёсткому» 0.7/0.5 |

## Незакрытые пункты CSV с ответами (для полноты — не блокируют MVP)

Два вопроса в выгрузке CSV имеют явно смещённые ответы (текст ответа на самом деле относится
к соседнему вопросу — видно по содержанию): тема 6 «RBAC, роли и интеграция с LDAP/AD» и
тема 15 «Несанкционированный доступ: определение, целевая метка и данные». Их реальные
ответы в этой выгрузке отсутствуют. Не блокирует текущий объём (направление «отказ датчика»
не требует ответа по НСД; по RBAC достаточно подтверждений из тем 10 и 12), но стоит уточнить
у организаторов при возможности до сдачи презентации.
