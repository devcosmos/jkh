# ТЗ: тренд деградации канала (доп. сигнал внутри «Отказ датчика»)

Статус: не реализовано, спецификация для отдельной сессии реализации. Написано 20 сентября
2026 года по итогам обсуждения — этот файл самодостаточен, реализующая сессия не обязана
читать историю чата, откуда он появился.

## 1. Контекст и почему это НЕ направление «Износ инфраструктуры»

Официальное ТЗ (`docs/ТЗ_сайта.md`) допускает четыре направления прогнозирования, из них
реализовано только «Отказ датчика» — единственное, по которому организаторы предоставили
полные данные. Направление «Износ инфраструктуры» требует «данных визуальных обследований
ОЭ, возраста оборудования... и внешних факторов (погода, сезон)» — организаторы прямо
подтвердили (`docs/Матрица_соответствия_ТЗ.md`, раздел про реестр оборудования; темы 7 и 9
`Город 8. ДЖКХ.xlsx - Вопросы_нормализованные_и_Ответы.csv`), что реестра оборудования с
датами ввода в эксплуатацию не будет никогда. Строить «Износ инфраструктуры» по-настоящему
нечем — придётся либо выдумать возраст оборудования, либо не использовать заявленные
признаки. Оба варианта противоречат принципу проекта: никогда не подставлять данные, которых
нет (см. `docs/data-audit.md`, `docs/label-policy.md` — весь проект держится на честном
признании пробелов вместо их маскировки).

**Что здесь предлагается вместо этого** — не новое направление ТЗ, а дополнительный
аналитический разрез **внутри уже реализованного** «Отказ датчика»: используя только реально
существующие данные (`incident_episodes` — уже очищенные эпизоды неисправности), показать,
растёт или падает частота эпизодов у конкретного канала со временем. Это законный прокси-сигнал
(«этот канал в последнее время стал давать сбои чаще») — не прогноз физического износа по
возрасту оборудования, и это разграничение обязательно к соблюдению везде: в названиях
переменных/эндпоинтов, в подписях UI, в документации. Ниже — правило именования (раздел 7).

**Не делать:** не называть эту фичу «износ», «wear», «degradation of equipment» ни в коде,
ни в UI-тексте — только «тренд по каналу» / «частота эпизодов» / «динамика неисправностей».
Не связывать её с возрастом оборудования, датой установки или регламентом ТО — этих данных
нет и не будет.

## 2. Источник данных

Таблица `incident_episodes` (`backend/app/models/entities.py`, класс `IncidentEpisode`):

```python
id, channel_id, sensor_type, start_time, end_time,
source: EpisodeSource, is_flapping_incident: bool,
left_censored: bool, right_censored: bool,
label_policy_version, notes
```

Важно (см. `docs/label-policy.md`, раздел 2):
- Эта таблица наполняется **только** разовым импортом (`scripts/build_episodes.py` →
  `import_analysis_to_db.py`, функция `import_episodes`). Живой воркер
  (`backend/app/workers/replay_worker.py`) её не пишет и не читает — это статичный
  исторический срез (на момент написания: 2024-01-01..2026-06-30, 182 524 строки,
  2468 каналов). **Не полагаться на то, что данные растут во времени** — окна анализа нужно
  считать от максимальной даты в самой таблице, а не от `datetime.now()`.
- **`is_flapping_incident = True` — это отфильтрованный день-дребезг, не отказ.** Такие
  строки при подсчёте частоты эпизодов **обязательно исключать** (`WHERE is_flapping_incident
  = false`), иначе тренд будет мерить шум канала, а не реальные эпизоды. Проверено: из
  182 524 строк 123 535 — флаппинг, 58 989 — «чистые» эпизоды. Именно эти 58 989 — объект
  анализа.
- `left_censored = True` означает, что эпизод уже шёл на момент начала наблюдения — не
  считать его «новым» эпизодом при разбиении на окна, где он попадает на границу (уже
  реализованное правило проекта, см. `label-policy.md`, раздел 4).

## 3. Известная ловушка (уже наступали на неё в этом проекте)

`frontend/src/pages/JournalPage.tsx` в этом же проекте один раз уже ломался ровно на этой
ошибке: сравнение исторических дат с реальными часами браузера помечало всё как «устаревшее»,
потому что данные датированы прошлым/условным периодом, а `Date.now()` — нет. Решение тогда —
считать «свежесть» от максимальной даты в самой выборке (`latestKnown`), а не от реальных
часов. **Здесь та же ловушка**: `as_of` для окон анализа должен браться как
`SELECT max(start_time) FROM incident_episodes` (или переиспользоваться закешированным
значением), а не `datetime.now(timezone.utc)`. Если это не учесть, «недавнее» окно окажется
почти пустым и все каналы получат бессмысленный результат.

## 4. Определение метрики (рабочая эвристика — как debounce/flapping пороги в label-policy.md)

Для канала `c` и точки отсчёта `as_of = max(start_time)` по всей таблице:

- **recent** — количество эпизодов с `is_flapping_incident=false` и
  `start_time > as_of - 90 дней` и `start_time <= as_of`.
- **baseline** — количество эпизодов с теми же условиями и
  `start_time > as_of - 180 дней` и `start_time <= as_of - 90 дней`.
- `total = recent + baseline`.

Классификация (пороги — рабочая эвристика, ревизуема, зафиксировать это же примечание в
docstring реализации, как это сделано для AUTO_CLOSE_AFTER_HOURS/флаппинг-порога):

| Условие | Статус | Смысл |
| --- | --- | --- |
| `total < 3` | `insufficient_data` | Слишком мало эпизодов, чтобы делать вывод — не показывать как «стабильно», это будет ложной уверенностью |
| `recent >= baseline * 1.5` и `recent - baseline >= 2` | `worsening` | Частота эпизодов заметно растёт |
| `recent <= baseline * 0.67` и `baseline - recent >= 2` | `improving` | Частота эпизодов заметно падает |
| иначе | `stable` | Нет выраженного тренда |

90/180 дней — выбор по аналогии с уже принятыми в проекте окнами (48ч автозакрытие, 24ч
горизонт прогноза) — достаточно длинные, чтобы не шуметь на редких эпизодах, достаточно
короткие, чтобы отражать «в последнее время». Порог `1.5`/`0.67` и минимум `total < 3` —
сознательно консервативные (см. `MIN_BIN_SIZE = 30` в `scripts/compute_calibration.py` и
`reliable`-флаг там же — тот же принцип: явно помечать ненадёжный результат, а не молчать
о нём).

## 5. Backend

### 5.1 Новый модуль сервиса

`backend/app/services/degradation_trend.py` (по прецеденту
`backend/app/services/maintenance_requests.py` — общая бизнес-логика, не привязанная к
конкретному роутеру):

```python
RECENT_WINDOW_DAYS = 90
BASELINE_WINDOW_DAYS = 90  # предшествующее окно той же длины
MIN_TOTAL_EPISODES = 3
WORSENING_RATIO = 1.5
IMPROVING_RATIO = 0.67
MIN_ABSOLUTE_DELTA = 2

def get_as_of(db) -> dt.datetime: ...  # max(start_time), кешировать в пределах запроса

def compute_trend_for_channels(db, channel_ids: list[int]) -> dict[int, dict]:
    """Одним SQL-запросом (два условных COUNT(*) FILTER) по всем переданным channel_id —
    без N+1. Возвращает {channel_id: {"recent": int, "baseline": int, "status": str}}."""
```

Одним запросом (для группы каналов сразу, не по одному) — по прецеденту `_grouped_counts` в
`backend/app/api/dashboard.py` и `latest_probability`-подзапросу в `backend/app/api/risks.py`.
Пример SQL-формы (адаптировать под SQLAlchemy Core, не сырую строку):

```sql
SELECT channel_id,
       count(*) FILTER (WHERE start_time > :as_of - interval '90 days') AS recent,
       count(*) FILTER (WHERE start_time <= :as_of - interval '90 days'
                          AND start_time >  :as_of - interval '180 days') AS baseline
FROM incident_episodes
WHERE is_flapping_incident = false AND channel_id = ANY(:channel_ids)
GROUP BY channel_id
```

### 5.2 Эндпоинты

   риска. Ответ — новая Pydantic-схема `DegradationTrendOut` в `backend/app/schemas/schemas.py`:
   ```python
   class DegradationTrendOut(BaseModel):
       channel_id: int
       as_of: dt.datetime
       recent_window_days: int
       baseline_window_days: int
       recent_count: int
       baseline_count: int
   ```

   `RegistryPage.tsx`) необязательным query-параметром `include_trend: bool = False` — если
   `true`, посчитать тренд одним батч-запросом для уже отфильтрованной/пагинированной
   страницы каналов и добавить поле `degradation_trend: DegradationTrendOut | None` в
   `ChannelOut`. Не считать тренд по умолчанию (лишняя нагрузка, если фронту не нужно).
3. (P2, необязательно) `GET /dashboard/summary` — добавить `top_worsening_channels: [...]`

Уважать матрицу доступа (`get_accessible_object_ids`/`check_object_access` из

## 7. Обязательная формулировка в UI (честность, не выдумывать больше, чем есть)

Везде, где показывается тренд, должна быть возможность увидеть пояснение (tooltip/подпись),
буквально или близко к тексту:

> Динамика частоты эпизодов неисправности за последние 90 дней против предыдущих 90 — не
> прогноз износа оборудования (данных о возрасте/дате установки нет), а наблюдаемый факт по
> уже собранной истории.

Это не опционально — без этой оговорки функция создаёт ложное впечатление, что система
что-то знает про физический износ, чего на самом деле нет.

`backend/tests/test_auto_close_stale_risk_cases.py` (там уже есть паттерн создания
`Channel`+фикстур и работы с временными окнами):

- Канал с `recent=6, baseline=2` (флаппинг-эпизоды подмешать отдельно с
  `is_flapping_incident=True` и убедиться, что они НЕ учтены) → `status == "worsening"`.

  эпизода с окном, а факт его начала в окне — `start_time` уже однозначен), но стоит явным
  тестом зафиксировать, что фильтр по датам работает по `start_time`, не по `end_time`.
- Батч-версия (`compute_trend_for_channels`) даёt тот же результат для нескольких каналов
  одним вызовом, что и поканальный расчёт — тест на согласованность.
- API-тест: `GET /channels/{id}/degradation-trend` возвращает 200 и ожидаемые поля;
  `GET /channels?include_trend=true` добавляет поле в каждый элемент списка.

Прогнать весь набор (`cd backend && python -m pytest -q`, через `.venv` в корне репозитория,

## 11. Что сознательно не входит в объём (P3, не делать без отдельного запроса)

- Прогноз тренда вперёд (регрессия/экстраполяция) — здесь только описательная статистика по
  двум окнам, не прогнозная модель.
- Учёт сезонности/погоды — нет данных, эта же причина, по которой не делается «Износ
  инфраструктуры» целиком.
- Агрегация тренда на уровень объекта (по аналогии с `/objects/tree`) — можно добавить
  позже отдельным запросом, не блокирует эту задачу.
