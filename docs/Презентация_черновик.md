Два поля на слайде:

  составляющая»):

- _Маркетинговая суть решения_ (подсказка шаблона: «идеи по дальнейшему применению,
  развитию или внедрению проекта»):

  выездов «по факту поломки» за счёт превентивного обслуживания и снимает с диспетчера

  не требует облачной инфраструктуры, дальше масштабируется на другие типы датчиков и

## Слайды 12-29 — содержательная часть (рекомендательные, свободная структура)

Шаблон подсказывает на служебном слайде (в исходнике — №4) структуру «01-06» для
продуктовых решений — ниже черновик по этим темам, раскладывайте по слайдам 12-29 как
удобно команде.

### 01. Маркетинговая часть решения

Диспетчеры ОДС физически не могут одинаково внимательно следить за тысячами каналов
датчиков — типовая реакция на инцидент наступает постфактум, когда отказ уже произошёл.
Наш сервис расставляет приоритеты за диспетчера: превращает поток сырых показаний в
короткий список «на что посмотреть в первую очередь» с понятным объяснением, почему
именно этот канал рискует отказать в ближайшие сутки.

### 02. Бизнесовая составляющая решения

- Снижает число реагирований «по факту поломки» за счёт превентивного обслуживания —
  меньше аварийных выездов, меньше жалоб жителей на внезапные отключения.
- Автоматическое формирование заявок по правилу убирает ручной шаг «увидел риск → создал
  заявку» — диспетчер только подтверждает или отклоняет, не печатает вручную.
- Полный аудит решений диспетчера — прозрачность для проверки качества работы ОДС.
- Развёртывается одним `docker compose` на своём сервере — не требует облачной
  инфраструктуры или лицензий на СУБД (PostgreSQL, открытый стек).

### 03. Техническая проработка решения

- **Данные:** аудит 8 годовых архивов (2019–2026, ~313 млн событий), очищенные эпизоды
  отказа с двухслойным денойзингом (фильтр флаппинга + debounce), политика разметки
  без доступа к эксперту зафиксирована и обоснована (`docs/label-policy.md`).
- **ML:** два независимых `CatBoostClassifier` (насос/вентилятор, дым/газ) с честным
  временным train/validation/test и разрывом 24ч; SHAP-объяснение каждого прогноза;
  дополнительный необученный сигнал аномальности (IsolationForest) и тренд деградации
  канала (частота эпизодов за 90 дней) — оба независимы от основной модели.
- **Backend:** FastAPI + PostgreSQL, полная ORM-схема (12+ таблиц), JWT-авторизация с
  ролями и матрицей доступа по объектам, аудит всех действий, автогенерируемый OpenAPI.
- **Живой инференс:** фоновый worker проигрывает исторический поток через тот же путь
  обработки, что будет использовать реальный адаптер источника (СМВУ) — считает признаки
  и обновляет риски на лету, не разовым импортом.
- **Frontend:** React + TypeScript — дашборд рисков, схема объектов с цветовой
  индикацией, журнал прогнозов, заявки на обслуживание со сменой статусов.
- **Эксплуатационная готовность:** TLS (Let's Encrypt/Caddy), backup/restore
  (реально сработал на проде при инциденте с потерей данных пользователей — восстановлено
  точечно из бэкапа), нагрузочная проверка 20 параллельных пользователей — 0 ошибок на
  всех ключевых эндпоинтах.

### 04. Уникальность решения

- Не одна модель-заглушка, а **два независимых сигнала риска** (обученная модель +
  необученная аномальность) плюс **объяснимость каждого прогноза** (SHAP) — диспетчер
  видит не просто число, а причину.
- **Честная методология:** целевые Precision/Recall не достигнуты — и это прямо
  показано с разбором причин (`model_report_*.md`), а не скрыто за красивым дашбордом.
  Рабочая точка порога выбрана по эпизодной оценке, а не по формальной метрике.
- Полный сквозной сценарий работает на реальном развёрнутом прототипе
  (`jkh.devcosmos.ru`), а не только локально — с реальными данными конкурса
  (5400 каналов, 95 объектов, сотни тысяч эпизодов).

### 05–06. Планы по развитию решения

- Донастроить признаки и модель для трека дым/газ (сейчас есть эпизоды, модель обучена,
  но без такой же глубины проверки, как насос/вентилятор).
- Соответствие канал → физическое устройство (сейчас разрешение на уровне канала).
- Полная матрица доступа по подразделениям (сейчас — по объектам).
- Off-site копия резервных копий (сейчас бэкапы и сама БД на одном сервере — единая
  точка отказа на уровне диска).
- Push-уведомления диспетчеру вместо периодического опроса API (организаторы подтвердили,
  что это желательно, но не обязательно для MVP).
