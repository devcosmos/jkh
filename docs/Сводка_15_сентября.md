# Сводка за 15 сентября 2026 года

Один рабочий день, но по факту закрыт объём, который в календаре `Рабочее_ТЗ_MVP.md`
был распределён на дни 15–23 сентября (аудит → разметка → модель → backend → UI → карта/журнал/заявки →
replay). Это хорошо для темпа, но означает, что качественные гейты (метрики, тесты,
документация к сдаче) сейчас отстают от инфраструктуры — см. раздел «Риски» ниже.

## 1. Что сделано

### Данные
- Полный аудит: все 8 годовых архивов (2019–2026, ~313 млн событий, ~16 ГБ) распакованы,
  манифест с SHA-256, полный профиль по годам.
- Найден и обойдён дефект источника: встроенный повторный заголовок в `ext-journal-2025.csv`.
- Расследованы и объяснены две аномалии: флаппинг газовых каналов (6 ноября 2025, 2 часа,
  6 каналов) и трёхмесячный инцидент дымовых каналов (апрель–июнь 2021).
- Построены очищенные эпизоды отказа для 4 типов (насос, вентилятор, дым, газ) с
  двухслойным денойзингом (фильтр дневного флаппинга + debounce ≥1 час), проверена
  устойчивость к порогам.
- Зафиксирована политика разметки без доступа к эксперту (`docs/label-policy.md`) —
  косвенная цель «переход в устойчивое состояние “Неисправен”», список вопросов на будущее.

### ML
- Витрина признаков на часовой сетке (окна 1ч/24ч/7сут, свежесть, соседи по расположению)
  для насоса/вентилятора, 2024–2026.
- Обучены базовая линия и CatBoost с честным временным train/validation/test.
- Эпизодная оценка (доля пойманных эпизодов, ложные тревоги/100 устройств/сутки).
- Эксперимент с признаком «соседи в отказе» — неоднозначный результат, задокументирован.
- **Целевые метрики (Precision>0.7, Recall>0.5) не достигнуты** ни на одной итерации —
  честно зафиксировано с разбором причин в `docs/analysis/model_report_насос_вентилятор.md`.

### Backend
- Полная схема БД (12+ таблиц) по разделу 7.3 плана, локальная JWT-авторизация с ролями,
  обязательный контур API (объекты, риски/решения, журнал прогнозов, заявки со сменой
  статуса, версия модели, health-checks).

### Frontend
- React + TypeScript + Leaflet, три раздела («Риски» список/карта/карточка, «Журнал»,
  «Заявки»), явные состояния загрузка/пусто/ошибка/устарело.

### Инфраструктура
- Развёрнуто на реальном VPS (159.194.249.102, домен `jkh.devcosmos.ru`), TLS через Caddy
  (Let's Encrypt, автообновление), Postgres не публикуется наружу.
- **По пути найден и исправлен реальный баг безопасности:** пустой `ports: []` в
  Compose-оверлее не убирал порты из базового файла — обнаружено и устранено до того, как
  стало постоянной дырой.
- БД наполнена реальными данными: 5400 каналов, 95 объектов, 182 524 эпизода, 2928
  риск-кейсов, 72 671 прогноз (исторический бэкфилл на test-периоде).
- Фоновый worker (replay + живой инференс): продвигает виртуальное время, кормит события,
  считает признаки и прогоняет через модель на живую, с сохраняемым курсором возобновления.

## 2. Что реализовано и работает прямо сейчас

Проверено сквозным образом на `https://jkh.devcosmos.ru/`:
- Логин → список рисков/карта/журнал/заявки с реальными данными.
- Диспетчер может принять решение по риск-кейсу (`observe/dispatch/reject/clarify`),
  сменить статус заявки по разрешённым переходам.
- Worker создаёт новые прогнозы и риск-кейсы в реальном времени (виртуальном), не только
  разовый импорт.
- Аудит изменений статусов пишется в БД.

## 3. Что НЕ реализовано (открытые пробелы)

| Пробел | Почему это важно |
| --- | --- |
| Целевые ML-метрики не достигнуты | Главное конкурсное требование — нужно либо улучшить, либо честно принять и обосновать в презентации |
| Автосоздание черновика заявки по правилу | Обязательный модуль по дополнению сайта — сейчас заявки создавались только вручную в импорте |
| Соответствие канал→устройство | Ограничивает точность эпизодов уровнем канала, а не физического устройства |
| Дым/газ: только эпизоды, без признаков/модели | Есть данные и потенциал (раздел 6.6 аудита показал их конкурентоспособность), но не доведено до модели |
| Геометрия объектов (карта) | 0 из 95 объектов с координатами — карта показывает честную пустоту, но не закрывает требование организатора |
| Матрица доступа по объектам/подразделениям | Сейчас RBAC только на уровне роли, не объекта |
| LDAP/AD | Локальная авторизация — принято решение как временное для MVP |
| Смена пароля | Endpoint отсутствует — пароль администратора нужно менять вручную в БД |
| Backup/restore | Не настроено и не проверено (требование ≤4 часа восстановления) |
| Нагрузочное тестирование (20 пользователей) | Не проводилось |
| Модульные/интеграционные тесты | Не написаны вообще |
| Git-репозиторий | Ещё не инициализирован — вся история изменений пока только в файловой системе |
| Документация к сдаче (презентация, DOCX, матрица соответствия) | Не начата |
| Источник событий worker'а | Заранее подготовленный файл, а не настоящий адаптер СМВУ (внешняя зависимость, не наша) |
| Причина аномалии 2021 (дым) | Локализована, но точная причина не установлена (нужны внешние данные) |

## 4. Рекомендации: куда двигаться дальше

По убыванию приоритета с учётом дедлайна 29 сентября и контрольных точек рабочего ТЗ:

1. **Инициализировать git и сделать первый коммит.** Сейчас весь этот объём работы не
   версионирован — риск потери при любой ошибке. Это буквально ничего не стоит и должно
   было быть первым шагом.
2. **Автосоздание черновика заявки по правилу** — логичное продолжение worker'а (когда
   риск-кейс открывается, сразу формировать черновик по шаблону из раздела 10 плана).
   Дёшево, закрывает обязательный модуль.
3. **Определиться с ML:** либо (а) попробовать ещё 1-2 гипотезы по улучшению признаков
   (дневная гранулярность, дым/газ) с жёстким дедлайном по времени, либо (б) принять
   текущий результат и сфокусироваться на честной презентации ограничения — это ключевое
   решение по контрольной точке 23 сентября рабочего ТЗ («весь сценарий до заявки
   работает; при отставании — только одна модель, базовые объяснения»).
4. **Написать хотя бы минимальный набор тестов** на критичные места: дедупликация событий,
   границы эпизода, переходы статусов заявки, права доступа — рабочее ТЗ явно требует
   доказательства качества, не только рабочий UI.
5. **Backup/restore на реальном сервере** — сейчас единственная точка отказа: если
   контейнер `db` потеряет volume, всё потеряно без возможности восстановления.
6. Позже, ближе к 24–26 сентября: нагрузочный тест, документация, презентация,
   репетиция на чистом окружении.

## 5. Что ещё предстоит решить (вопросы, не закрытые техникой)

- **Доступ к эксперту** — по-прежнему не подключён. Debounce-порог (1 час) и порог
  флаппинга (10/день) — рабочие эвристики, не согласованные значения.
- **Статус дыма/газа** — оставлять «экспериментом» или поднимать до второго проверенного
  типа наравне с насосом/вентилятором? Данные (раздел 6.6 аудита) говорят в пользу второго.
- **Честная формулировка в презентации**, что цель — прогноз перехода в состояние
  "Неисправен", а не подтверждённый физический отказ (правило 5.1(2) рабочего ТЗ).
- **Судьба недостигнутых метрик** — заявлять как ограничение прототипа (разрешено правилом
  5.1(7)) или продолжать попытки улучшения в оставшееся время. Это решение пользователя,
  зависящее от приоритетов на оставшиеся ~13 дней.
- **Смена пароля администратора и ротация секретов** перед показом кому-либо ещё.
- **VPS**: сервер и домен оформлены, но нет backup-плана и нагрузочного теста — стоит
  решить, достаточно ли текущей конфигурации (4 vCPU/8 ГБ) под демо-нагрузку или нужно
  что-то менять заранее, а не в последний момент.
