# Рабочее ТЗ: конкурсный прототип ЖКХ к 29 сентября 2026 года

Обновлено: 15 сентября 2026 года.

## 1. Ограничения и цель

- Исполнитель: один разработчик, пользователь; Codex помогает с анализом, кодом, проверками и документацией.
- Крайний срок: **29 сентября 2026 года**. Точное время закрытия платформы нужно проверить. Внутренняя цель — отправить комплект **28 сентября**, 29 сентября оставить на исправление проблем со сдачей.
- Рабочее окно: 15–28 сентября, 14 календарных дней. Доступные часы в день не установлены; календарь задаёт приоритеты и контрольные точки, а не гарантию трудозатрат.
- Результат: воспроизводимый прототип по одной категории «Отказ датчика» с ML-моделью, интерфейсом диспетчера, заявками, REST API и доказательствами качества.
- Промышленное внедрение и дополнительные категории выходят за двухнедельный объём.

Основания: [основное ТЗ](../ЖКХ.md), [дополнение сайта](ТЗ_сайта.md), [технический план](План_реализации.md). Этот документ фиксирует наш объём разработки. Он не отменяет требования организатора: каждый отложенный пункт должен быть отмечен в итоговой матрице соответствия.

## 2. Обязательный объём к сдаче

| Блок | Реализация в прототипе | Проверка |
| --- | --- | --- |
| Категория | «Отказ датчика»; проверенные типы выбираются по аудиту до 17 сентября | Зафиксированы типы, количество устройств и независимых эпизодов |
| Данные | Пакетный импорт имеющихся CSV; CLI-импорт XLSX без отдельного интерфейса загрузки | Схема, дедупликация, сортировка по времени, отчёт отклонённых строк |
| Исторический период | Сначала доступные распакованные 2025–2026 годы; короткий срез для проверки кода, затем достаточный период для разметки и оценки | Периоды train/validation/test выбираются по датам и наличию эпизодов, а не удобству метрики |
| Разметка | Новый эпизод отказа; текущая неисправность исключена из прогноза нового отказа | Проверка семантики состояний и доступного подтверждения; неизвестные исходы исключены |
| ML | Одна простая базовая линия и один CatBoost-кандидат | Временная validation, фиксированный порог, независимый test |
| Горизонт | Риск нового события в ближайшие 24 часа | Окно отражено в метке, API и UI; фактическое опережение измеряется отдельно |
| Метрики | Цель Precision > 0.7 и Recall > 0.5 по заявленной категории | TP/FP/FN, число эпизодов, метрики по окнам и эпизодам; недостижение честно отмечается |
| Поток | Проигрывание исторических событий через тот же путь обработки, что будет использовать адаптер источника | Нет доступа к будущим данным, обработаны повторы и устаревание |
| REST API | Объекты, риски, история, решения, заявки, состояние сервиса; OpenAPI | UI получает реальные данные из API, изменения сохраняются |
| Дашборд | Приоритетный список, фильтры, категория, вероятность, окно, свежесть | Видны нормальное, пустое, ошибочное и устаревшее состояния |
| Карточка | Устройство, объект, история, факторы риска, действие диспетчера | Прогноз и текущая неисправность различаются |
| Карта | Минимальный слой проверенных объектов с карточкой риска | Геометрия подтверждена; объекты без координат посчитаны отдельно |
| Журнал | Сохранённые прогнозы и решения с временем и версией модели | История доступна после перезапуска |
| Заявки | Автоматический локальный черновик по правилу; утверждение, завершение, отклонение | Повтор прогноза не создаёт дубликат; решение принимает человек |
| Доступ | Локальный вход, роли диспетчера и администратора, аудит изменений | Проверка доступа на backend; секреты вне репозитория |
| Запуск | Один сервер, Docker Compose, инструкция, ограниченный демонабор | Запуск на чистом окружении, повторяемый демосценарий |
| Сдача | Репозиторий, доступный прототип, презентация PPTX/PDF, документация DOCX/PDF, отчёт ML | Все ссылки открываются; доступ и инструкции проверены |

Карта остаётся обязательным требованием организатора. Если геоданных нет, дерево объектов и явно подписанная схема позволяют показать сценарий, но не закрывают требование реальной карты. Аналогично replay демонстрирует обработку потока, но не доказывает подключение к рабочей СМВУ.

## 3. Минимальная архитектура

- Backend: FastAPI и PostgreSQL, один кодовый проект с модулями импорта, прогнозов и заявок.
- Фоновая обработка: один отдельный Python worker; простая сохраняемая очередь/таблица заданий, без брокера сообщений.
- История и ML: DuckDB/Parquet, общая функция признаков для обучения и воспроизведения; версия модели и конфигурация рядом с отчётом.
- Frontend: React + TypeScript, один общий макет. Три раздела: «Риски» с переключением списка/карты и карточкой, «Журнал», «Заявки».
- Обновление UI: периодический опрос API. Отдельный realtime-сервис не нужен.
- Развёртывание: Docker Compose. TLS обязателен при публикации прототипа в сеть.
- Рекомендации и заявки: шаблоны и правила, без LLM в рабочем контуре.

До сдачи не менять стек без блокирующей причины. Предпочитать сквозную работающую функцию отдельному сложному модулю.

## 4. Что не входит в двухнедельную реализацию

| Пункт | Решение и статус относительно исходного ТЗ |
| --- | --- |
| Пожар, доступ, износ, подтопления | Отложены; сайт разрешает выбрать одну категорию |
| Полная обработка всей истории 12+ лет | Манифест всех файлов обязателен; обучение на достаточном проверенном периоде. Полнота многолетнего покрытия не заявляется |
| Подключение рабочих СМВУ/ОДС, СКУД, АРМ-Контроль | Контракт и место подключения адаптера; реальный доступ — внешняя зависимость, не закрытая имитатором |
| LDAP/AD | Локальная авторизация в прототипе; корпоративная интеграция остаётся незакрытым требованием |
| Автоматическое дообучение | Воспроизводимый ручной запуск обучения и замена проверенной версии; автоматизация позже |
| Внешняя отправка заявок | Только собственная БД и экспорт; учитывается read-only ограничение основного ТЗ |
| Расширенные отчёты, календарь бригад, мобильная версия | Отложены; не нужны для основного сквозного сценария |
| Универсальные XML/SQL-коннекторы и редактор схем импорта | Отложены, поддерживаются реально используемые форматы; пробелы указать в матрице |
| Промышленная отказоустойчивость и полноценный мониторинг | Логи, healthcheck, резервное копирование и проверка восстановления прототипа сейчас; промышленный регламент позже |
| Kafka, Kubernetes, микросервисы, отдельный feature store | Не включать в архитектуру прототипа |

Нагрузку на 20 пользователей, время прогноза < 300 секунд и восстановление ≤ 4 часа проверяем в масштабе прототипа. Успех на небольшом наборе не выдаём за доказанную производительность на всей инфраструктуре.

## 5. Правила работы с моделью

1. До 17 сентября определить, что означает «Неисправен», какие типы можно использовать и какие события независимы.
2. Если независимого подтверждения нет, явно назвать цель «прогноз перехода в состояние “Неисправен”». Это косвенная метка; метрики на ней не доказывают качество прогноза физических отказов.
3. Не использовать `тревожное` как готовую метку поломки. Не включать будущее состояние, итог ремонта или последующее решение диспетчера в признаки.
4. Убрать дубли и пересечение файлов до разбиения. Train, validation и test разделить по времени; исключить пересечение будущих окон и эпизодов между частями.
5. Начальные окна признаков: 1 час, 24 часа и 7 суток. Окна 6 часов и 30 суток добавлять только при измеренном улучшении validation и наличии времени.
6. До 23 сентября разрешены эксперименты с признаками и порогом. На 24 сентября закрепить модель, правила и тестовую выборку; выполнить финальную оценку.
7. Если порог не обеспечивает одновременно Precision > 0.7 и Recall > 0.5, зафиксировать недостижение. Не менять test и не подбирать порог на нём.
8. После открытия test допустимы исправления ошибок, но результат уже не считается независимым после настройки на этих данных. Существенные изменения требуют нового закрытого периода либо явного описания ограничения.
9. Уже возникший отказ показывать отдельно. Недостаток данных не превращать в низкий риск.

## 7. Контрольные точки и сокращение объёма

- **17 сентября:** пригодная постановка ML либо явный статус косвенной разметки. Если меток нет, сразу фиксируем невозможность доказать требуемое качество; не тратим остаток срока на перебор моделей без цели.
- **20 сентября:** прогноз из реальных данных виден через API и UI. При отставании сокращаем визуальную отделку и дополнительные фильтры.
- **23 сентября:** весь сценарий до заявки работает. При отставании оставляем только одну модель, проверенные типы, базовые объяснения и необходимые статусы.
- **24 сентября:** прекращаем расширение функций и эксперименты. Оставшееся время защищено для проверок, исправлений и материалов.
- **27 сентября:** комплект пригоден к отправке. Некритичные дефекты идут в известные ограничения.

Сначала сокращать украшения, дополнительные графики, настройки, универсальность импорта и дополнительные типы внутри исследуемого направления. Сохранять достоверность метрик, временную корректность, API, журнал решений, автоматические черновики и воспроизводимый запуск. Отсутствующую обязательную функцию отмечать как пробел, а не объявлять ненужной.

## 8. Организация работы одного разработчика с Codex

- Пользователь определяет продуктовые решения, получает внешние данные/доступы, проверяет сценарий глазами диспетчера и отправляет комплект.
- Codex по задачам помогает готовить данные, писать код, проверять результат, исправлять ошибки и обновлять документацию.
- Один текущий этап и проверяемый результат перед следующим; не планировать независимые человеческие команды.
- В конце каждой рабочей сессии фиксировать сделанное, команду запуска, проверки, ограничения и следующий конкретный шаг в `docs/Статус.md` после начала реализации.
- Не обещать экономию выездов, промышленную готовность или достижение ML-метрик без измерений.
