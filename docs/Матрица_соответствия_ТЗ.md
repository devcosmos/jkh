## Раздел 6. Общие требования к сервису

| Требование | Статус | Реализация / обоснование |

| Горизонт прогноза ≥ 24 часов | ✅ | Целевая переменная `y(t)` на `(t, t+24ч]` — `docs/label-policy.md`. Тема 19 CSV: организаторы подтвердили, что 24ч — целевое значение по умолчанию, отклонения допустимы при обосновании |

| Классификация типов инцидентов | 🟡 | Одна категория «Отказ датчика» реализована как продакшн-путь (насос/вентилятор + дым/газ — см. ниже). | Работа с журналами ОДС и реестром оборудования | ⛔ | Не будут предоставлены организаторами (темы 7, 9 CSV: ОДС — отдельная Django-система без интеграции, реестр оборудования не передан и не будет передан). Заменено имитацией: решения диспетчера пишутся в собственный журнал (`Decision`), для наработки на отказ рекомендовано использовать усреднённые данные из открытых источников (тема 9 CSV) — не реализовано в эту итерацию, открытый пробел |

## Раздел 7. Требования к обработке данных

| Требование | Статус | Реализация / обоснование |
| --- | --- | --- |
| Импорт CSV/XLSX | ✅ | `scripts/import_analysis_to_db.py` (CSV); XLSX не встречался в реальных данных конкурса |

Хранение WKT в БД оставлено (`Object.geometry_wkt`, всегда пусто на текущих данных, честно отражено в `/objects/geojson`), а основной интерфейс — иерархическая схема объектов с цветовой индикацией риска (`/objects/tree`, `frontend/src/components/ObjectsTree.tsx`) — организаторы сами рекомендуют именно такое решение при отсутствии координат |

## Раздел 9. Производительность и качество прогнозирования

| Требование | Статус | Реализация / обоснование |
| --- | --- | --- |
| Inference ≤ 5 минут на объект | ✅ | Тик воркера — секунды на весь пакет каналов, см. `Статус.md` |
| Precision/Recall — «определяются на этапе проектирования исходя из качества данных» (раздел 9 ЖКХ.md) | 🟡 | Целевые Precision>0.7/Recall>0.5 из `ТЗ_сайта.md` не достигнуты ни для насос/вентилятор (`docs/analysis/model_report_насос_вентилятор.md`), ни для дым/газ (`model_report_дым_газ.md`). Тема 3 CSV подтверждает: «указанные значения являются плановыми, а не жёсткими требованиями… если данные не позволяют достичь этих уровней, их можно снизить, обязательно обосновав». Обоснование: сигнал в данных (история состояний самого канала) статистически слаб — ROC-AUC 0.71/0.63 против случайных 0.5, но PR-AUC на два порядка ниже требуемой точности; три проверенные гипотезы улучшения (соседние устройства, дневная гранулярность, числовые каналы) не дали качественного прорыва. Рабочая точка порога выбрана по эпизодной оценке (`scripts/evaluate_episodes*.py`), а не по «жёсткому» 0.7/0.5 |
