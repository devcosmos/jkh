## Итоговый продукт (docs/ТЗ_сайта.md, раздел «Описание итогового продукта»)

Формулировка задачи с сайта: «Разработайте веб сервис, использующий предиктивную ML-модель...
Программный продукт (сервис): предиктивная ML-модель прогнозирования аварий и отказов
оборудования + веб-интерфейс диспетчера ОДС с дашбордом рисков, картой объектов и журналом
прогнозов + модуль автоматического формирования заявок на превентивное обслуживание + REST API».
Все четыре компонента реализованы:

| Компонент | Статус | Реализация |
| --- | --- | --- |
| Предиктивная ML-модель | ✅ | Не скрипт с эвристикой, а два независимо обученных `CatBoostClassifier` (по одному на трек «Отказ датчика»: насос/вентилятор и дым/газ — направление прямо названо в ТЗ, строка 17) — реальные train/val/test с разрывом 24ч (`scripts/train_model*.py`), метрики зафиксированы в `docs/analysis/model_report_*.md`. В проде инференс живой: `backend/app/workers/replay_worker.py` на каждом тике считает признаки из потока событий и вызывает `model.predict_proba(...)` на загруженном `.cbm`-артефакте — не захардкожено. Дополнительно: SHAP-объяснение конкретного прогноза (`explain_prediction`) и независимый сигнал аномальности — `IsolationForest` без учителя на тех же поведенческих признаках (`scripts/train_anomaly_model.py`), обучен отдельно от CatBoost и способен отметить поведение вне размеченных сценариев отказа. Ещё один доп. сигнал внутри того же направления — тренд частоты эпизодов по каналу (растёт/падает за 90 дней), реализованный 21 сентября (`backend/app/services/degradation_trend.py`, `docs/ТЗ_тренд_деградации_канала.md`) — не путать со строкой «Износ инфраструктуры» ниже: это разные вещи, тренд не опирается на возраст/дату установки оборудования |
| Веб-интерфейс диспетчера: дашборд рисков, карта объектов, журнал прогнозов | ✅ | `frontend/src/pages/DashboardPage.tsx` (обзор с показателями), `RisksPage.tsx` (дашборд рисков + схема объектов вместо GPS-карты — по прямой рекомендации организаторов, координат не будет никогда, тема 14 CSV), `JournalPage.tsx` (журнал прогнозов) |
| Модуль автоформирования заявок на превентивное обслуживание | ✅ | Автосоздание по правилу при открытии риск-кейса (`replay_worker.maybe_create_draft_request`) и по явному решению диспетчера «направить на проверку» (`app/services/maintenance_requests.ensure_request_for_dispatch`, добавлено 20 сентября — раньше решение и заявка были не связаны). Полный жизненный цикл — `frontend/src/pages/RequestsPage.tsx` |
| REST API | ✅ | FastAPI, `backend/app/api/*`, автогенерируемая OpenAPI-схема |

Целевые метрики раздела («Precision > 0.7 и Recall > 0.5», горизонт ≥24ч, инференс <5 мин) —
см. раздел 9 ниже: горизонт и время инференса выполнены, Precision/Recall — плановая, не
жёсткая цель (тема 3 CSV), рабочая точка выбрана по эпизодной оценке и честно задокументирована.

**О четырёх направлениях прогнозирования (строки 17-20 `ТЗ_сайта.md`):** команда сознательно
сосредоточилась на «Отказ датчика» (строка 22 разрешает выбрать одно или несколько
направлений). Трек дым/газ по факту частично покрывает и направление «Пожарный риск» —
он использует те же дымовые/газовые датчики и ту же динамику показаний, которые в описании
«Пожарного риска» названы источником сигнала, — но не является отдельно заявленным
направлением и не претендует на полноту (нет данных АРМ-Контроль о графиках сварочных/горячих
работ, с которыми предполагается корреляция). «Несанкционированный доступ» и «Износ
инфраструктуры» не реализованы — данные СКУД/журналов допусков и визуальных обследований
организаторами не предоставлены.

## Раздел 6. Общие требования к сервису

| Требование | Статус | Реализация / обоснование |
| --- | --- | --- |
| Анализ данных с датчиков, расчёт вероятности инцидента | ✅ | `scripts/build_features*.py`, `scripts/train_model*.py`; воркер — `backend/app/workers/replay_worker.py` |
| Горизонт прогноза ≥ 24 часов | ✅ | Целевая переменная `y(t)` на `(t, t+24ч]` — `docs/label-policy.md`. Тема 19 CSV: организаторы подтвердили, что 24ч — целевое значение по умолчанию, отклонения допустимы при обосновании |
| Локация оборудования под риском | ✅ (после этой сессии) | `Channel.object_id` теперь заполняется из `ид_объект` обновлённого `справочник_каналов_датчиков.csv` (тема 4 CSV: организаторы прислали обновлённый файл со связью канал→объект) |
| Классификация типов инцидентов | 🟡 | Одна категория «Отказ датчика» реализована как продакшн-путь (насос/вентилятор + дым/газ — см. ниже). Пожар/НСД/износ/подтопление отложены — тема 18 CSV: организаторы подтвердили, что направления оцениваются независимо и жёсткого приоритета нет, команда вправе выбрать |
| Сценарный анализ (пожар/проникновение/подтопление) | ⛔ | Не входит в объём двух недель — `Рабочее_ТЗ_MVP.md`, раздел 4. Обоснование выбора — тема 18 CSV |
| Работа с журналами ОДС и реестром оборудования | 🟡 | Внешний реестр оборудования и интеграция с ОДС не будут предоставлены организаторами (темы 7, 9 CSV: ОДС — отдельная Django-система без интеграции, реестр оборудования не передан и не будет передан) — это остаётся ⛔. Но соответствие канал→физическое устройство (насос/вентилятор) теперь построено эвристически из собственных данных: `scripts/link_channels_to_devices.py` парсит идентификатор устройства (номер + пикет) из свободнотекстового названия датчика, покрывает 87.8% каналов насоса/вентилятора (469/534) — реальная идентичность устройства видна в заявках и на карточке канала (`Channel.device_label`/`.label`), а не голый ID канала. Дым/газ и остальные типы каналов таким способом не размечены — паттерн специфичен для насос/вентилятор. Решения диспетчера пишутся в собственный журнал (`Decision`) вместо интеграции с ОДС |

## Раздел 9. Производительность и качество прогнозирования

| Требование | Статус | Реализация / обоснование |
| --- | --- | --- |
| Inference ≤ 5 минут на объект | ✅ | Тик воркера — секунды на весь пакет каналов, см. `Статус.md` |
| Precision/Recall — «определяются на этапе проектирования исходя из качества данных» (раздел 9 ЖКХ.md) | 🟡 | Целевые Precision>0.7/Recall>0.5 из `ТЗ_сайта.md` не достигнуты ни для насос/вентилятор (`docs/analysis/model_report_насос_вентилятор.md`), ни для дым/газ (`model_report_дым_газ.md`). Тема 3 CSV подтверждает: «указанные значения являются плановыми, а не жёсткими требованиями… если данные не позволяют достичь этих уровней, их можно снизить, обязательно обосновав». Обоснование: сигнал в данных (история состояний самого канала) статистически слаб — ROC-AUC 0.71/0.63 против случайных 0.5, но PR-AUC на два порядка ниже требуемой точности; три проверенные гипотезы улучшения (соседние устройства, дневная гранулярность, числовые каналы) не дали качественного прорыва. Рабочая точка порога выбрана по эпизодной оценке (`scripts/evaluate_episodes*.py`), а не по «жёсткому» 0.7/0.5 |

## Незакрытые пункты CSV с ответами (для полноты — не блокируют MVP)

Два вопроса в выгрузке CSV имеют явно смещённые ответы (текст ответа на самом деле относится
к соседнему вопросу — видно по содержанию): тема 6 «RBAC, роли и интеграция с LDAP/AD» и
тема 15 «Несанкционированный доступ: определение, целевая метка и данные». Их реальные
ответы в этой выгрузке отсутствуют. Не блокирует текущий объём (направление «отказ датчика»
не требует ответа по НСД; по RBAC достаточно подтверждений из тем 10 и 12), но стоит уточнить
у организаторов при возможности до сдачи презентации.
