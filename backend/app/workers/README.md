# Worker: replay + живой инференс

`replay_worker.py` — единственный фоновый процесс прототипа (раздел 3 ТЗ MVP: «один
отдельный Python worker»). Что делает:

1. Продвигает виртуальное время часовыми тиками (курсор — таблица `replay_state`,
   переживает перезапуск контейнера).
2. "Доставляет" события из `docs/analysis/replay_feed_насос_вентилятор.parquet` (заранее
   подготовлен `scripts/build_replay_feed.py` — только насос/вентилятор, только с
   2025-07-01, честно "невиданный" моделью test-период) в оперативную таблицу
   `channel_events`, скользящее окно 7 суток (раздел 7.2 плана).
3. На каждом тике считает признаки (те же, что при обучении — `scripts/build_features.py`)
   напрямую SQL-запросами к `channel_events`, прогоняет через `catboost_насос_вентилятор.cbm`.
4. При вероятности ≥ порога (0.7, тот же провизорный порог, что и при бэкфилле) —
   находит открытый риск-кейс по каналу или создаёт новый, пишет `Prediction`.

## Честные ограничения

- Порог 0.7 не удовлетворяет целевым Precision>0.7/Recall>0.5 — см.
  `docs/analysis/model_report_насос_вентилятор.md`. Это демонстрация механизма, не
  подтверждение качества.
- Источник — заранее подготовленный файл, а не реальный адаптер СМВУ (тот остаётся внешней
  зависимостью, см. `План_реализации.md`, раздел 4 «Что не входит»).
- Только насос/вентилятор — дым/газ не подключены к worker'у (эпизоды для них в БД есть,
  витрины признаков и модели — нет, см. `docs/Статус.md`).
- Риск-кейсы не закрываются автоматически — только вручную через `/risk-cases/{id}/decisions`.
- Нет ретраев/dead-letter при сбое — при падении worker просто перезапускается
  (`restart: unless-stopped`) и продолжает с последнего сохранённого `virtual_time`.

## Локальный запуск

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-worker.txt
export JKH_DATABASE_URL=postgresql+psycopg://jkh:jkh@localhost:5433/jkh
export REPLAY_FEED_PATH=../data/replay_feed_насос_вентилятор.parquet
export REPLAY_MODEL_PATH=../data/catboost_насос_вентилятор.cbm
python3 -m app.workers.replay_worker
```

Скорость воспроизведения — `REPLAY_SLEEP_SECONDS` (по умолчанию 2 секунды реального времени
на 1 час виртуального; полный test-период ~1 год займёт часы непрерывной работы — это
ожидаемо для развёрнутого сервиса, а не для однократного просмотра).
