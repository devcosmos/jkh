# Развёртывание на VPS

## Требования к серверу

| Параметр | Рекомендация |
| --- | --- |
| CPU | 4 vCPU (минимум 2) |
| RAM | 8 ГБ (минимум 4) |
| Диск | 100 ГБ SSD (минимум 50) |
| ОС | Ubuntu 22.04/24.04 LTS |
| Сеть | публичный IP, открытые порты 80/443 (22 для SSH) |

Обоснование — раздел 11 ТЗ (Linux, PostgreSQL, TLS 1.2+) и раздел 3 рабочего ТЗ MVP
(«Один сервер, Docker Compose»). Оперативная БД небольшая (прогнозы/заявки/аудит,
не сырые 16 ГБ исторических CSV — те остаются локально для обучения и не идут на прод).

## Первоначальная настройка сервера

```bash
# на самом VPS, от sudo-пользователя
apt update && apt install -y docker.io docker-compose-plugin
usermod -aG docker $USER   # затем перелогиниться
```

## Разворачивание

```bash
git clone <репозиторий> jkh && cd jkh
cp .env.example .env   # заполнить реальные пароли/секреты — не коммитить
export DOMAIN=jkh.example.ru   # домен должен указывать A-записью на IP сервера
docker compose -f docker-compose.yml -f deploy/docker-compose.prod.yml up -d
docker compose exec backend alembic upgrade head
```

Caddy сам получит и обновит сертификат Let's Encrypt по домену `DOMAIN` — вручную
настраивать certbot/nginx не нужно.

переключение контейнеров на новую сборку с сохранением существующего тома БД (`jkh_pgdata`,
62047 риск-кейсов на момент миграции — не потеряны), `alembic upgrade head` до `b338f001508f`,
worker корректно продолжил replay с сохранённого `virtual_time` на обновлённом фиде событий
(cursor пересчитывается из `virtual_time`, не зависит от индексации конкретного файла — смена
содержимого `replay_feed_*.parquet` между старой и новой сборкой не потребовала сброса
состояния). Старая копия сохранена как `/opt/jkh-old-backup-20260922` (не удалена, можно
убрать после нескольких дней стабильной работы новой схемы).

С 22 сентября 2026 сервер обновляется из `git clone` (раньше — ручное копирование файлов,
без `.git`, что отставало от репозитория на десятки коммитов — см. `analys_and_todo.md`).
`deploy/auto_deploy.sh` опрашивается по cron, не по webhook: не нужно открывать порт для
GitHub или хранить SSH-секрет в GitHub Actions — на сервере уже стоит read-only deploy key.

Настройка (один раз):

```bash
# 1. Deploy key уже сгенерирован на сервере (~/.ssh/jkh_deploy_key) и добавлен в
#    GitHub → Settings → Deploy keys (без права записи).
# 2. cron — опрос раз в 2 минуты:
crontab -e
# */2 * * * * /opt/jkh/deploy/auto_deploy.sh
```

Скрипт ничего не делает, если `origin/main` не ушёл вперёд (`git fetch` + сравнение
`HEAD`/`origin/main`). При новых коммитах: `git reset --hard origin/main` (не трогает
`.env` и большие ML-артефакты — они не в индексе git вообще, не просто незакоммичены),
`docker compose build` (пересобирает только изменившиеся слои/сервисы), `up -d`,
`alembic upgrade head`. Лог — `deploy/auto_deploy.log`, не в git.

**Компромисс:** обновление приходит с задержкой до интервала опроса (2 минуты), не мгновенно
по push — сознательный выбор простоты и без открытых портов, а не webhook-задержка.

## Backup/restore (раздел 12 ТЗ: RTO ≤ 4 часа)

`deploy/backup.sh` — `pg_dump -Fc` из контейнера `db` в `<репозиторий>/backups/jkh_<UTC-время>.dump`
(каталог вне git, см. `.gitignore`), ротация — хранит дампы за последние 14 дней
(`JKH_BACKUP_RETENTION_DAYS`, если нужно другое число). `deploy/restore.sh <дамп>` —
останавливает `backend`/`worker`, `pg_restore --clean --if-exists` поверх текущей БД,
запускает их обратно; интерактивное подтверждение (пропускается, если стоит cron/без tty).

Первое измерение (15 сентября 2026) было на минимальном наборе данных, почти сразу после
запуска worker. При непрерывной работе worker'а объём растёт в основном за счёт
`predictions` (каждый тик — прогноз по каждому каналу трека) — переизмерено 22 сентября
2026 на реальном дев-инстансе (5400 каналов, 182 тыс. эпизодов, 62 тыс. риск-кейсов,
**3,57 млн прогнозов**, база на диске 2,6 ГБ): backup (`pg_dump -Fc`) — 59 МБ, ~7 сек;
restore (`pg_restore --clean --if-exists`) на пустую БД — ~23 сек; полный цикл backup →
потеря данных → restore → данные на месте подтверждён. Сотни ГБ по-прежнему не ожидаются
(сырые CSV на прод не идут, см. «Требования к серверу» выше), но `predictions` стоит
периодически чистить или архивировать на реальном длительном прогоне — иначе объём и время
backup/restore продолжат расти линейно с виртуальным временем worker'а, а не с реальным.
Даже так это на два порядка быстрее 4-часового норматива RTO.

Cron на VPS (от пользователя с доступом к docker, в каталоге репозитория):

```bash
crontab -e
# 0 3 * * * /opt/jkh/deploy/backup.sh >> /var/log/jkh-backup.log 2>&1
```

**Известное ограничение:** дампы сейчас хранятся на том же сервере, что и сама БД — при
потере диска сервера целиком теряются и данные, и бэкапы (единая точка отказа на уровне
диска, а не только контейнера). Раздел 3 рабочего ТЗ MVP описывает «один сервер», поэтому
это принятое для MVP упрощение, а не проглядели: следующий шаг для прод-контура — синхронизировать
`backups/` на внешнее хранилище (`rclone`/`rsync` на другой сервер или объектное хранилище),
что не сделано намеренно — нет доступа/учётных данных внешнего хранилища на момент написания.

## Полный протокол восстановления (OPS-04, `analys_and_todo.md`)

`backup.sh`/`restore.sh` покрывают только БД Postgres — этого **недостаточно** для
восстановления работающего приложения на новом сервере. Полное восстановление состоит из
трёх независимых источников, не одного:

1. **Код + демокомплект моделей** — `git clone`/`git pull` (шесть файлов `.cbm`/`.joblib`/
   `.parquet` в `artifacts/` отслеживаются в Git специально ради этого, см. корневой
   `.gitignore` и `README.md`).
2. **Секреты** (`.env` — пароль Postgres, `JWT_SECRET_KEY`, домен, ключ LLM) — намеренно вне
   Git (см. `.env.example`), сейчас хранятся только на самом сервере (в `/opt/jkh/.env` или
   эквиваленте). Отдельного бэкапа `.env` нет — если сервер теряется целиком, секреты нужно
   генерировать заново (`JWT_SECRET_KEY` — новый, все выданные токены инвалидируются; для
   `POSTGRES_PASSWORD` это не проблема, т.к. восстанавливается новая БД). Хранение `.env` во
   внешнем секрет-менеджере — не сделано намеренно, тот же открытый вопрос, что и внешнее
   хранение дампов БД выше.
3. **БД** — `backup.sh`/`restore.sh` (раздел выше).

**Репетиция восстановления проведена 22 сентября 2026** на изолированном окружении (не
трогая рабочий демо-стенд): снят реальный дамп рабочей БД (`backup.sh`, 60 МБ), восстановлен
в свежий одноразовый контейнер Postgres (`pg_restore --clean --if-exists`, без ошибок),
поднят backend поверх восстановленной БД. Проверено приложением, не только `pg_restore`
кодом возврата: `POST /auth/login` реальным паролем администратора выдаёт JWT,
`GET /risk-cases` и `GET /dashboard/summary` возвращают реальные данные (62047 риск-кейсов,
3,57 млн прогнозов — совпадает с источником), `GET /models/current` отдаёт обе версии
моделей с метриками. Контейнеры и временный дамп удалены после проверки.

## Ещё не сделано (честно, для матрицы соответствия)

- Отдельного бэкапа моделей/артефактов нет — восстанавливаются через Git (см. «Полный
  протокол восстановления» выше), не через `backup.sh`. Это осознанный выбор (демокомплект
  и так в Git), а не пробел — но только для шести committed-файлов; модель, переобученную
  и не закоммиченную, этот протокол не восстановит.
- `.env` (секреты) не бэкапится вообще, ни на сервере, ни во внешнем хранилище — см. «Полный
  протокол восстановления» выше.
- Off-site копия бэкапов БД (см. ограничение выше) — не настроена, нет внешнего хранилища.
- Домен и провайдер VPS ещё не выбраны пользователем на момент написания этого раздела
  (сервер и домен уже подняты позже — см. `docs/documentation/Технические_заметки.md`).
