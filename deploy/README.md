# Развёртывание на VPS

## Требования к серверу

| Параметр | Рекомендация |
| --- | --- |
| CPU | 4 vCPU (минимум 2) |
| RAM | 8 ГБ (минимум 4) |
| Диск | 100 ГБ SSD (минимум 50) |
| ОС | Ubuntu 22.04/24.04 LTS |
| Сеть | публичный IP, открытые порты 80/443 (22 для SSH) |

Обоснование — раздел 11 ТЗ (Linux, PostgreSQL, TLS 1.2+) и раздел 3 рабочего ТЗ MVP
(«Один сервер, Docker Compose»). Оперативная БД небольшая (прогнозы/заявки/аудит,
не сырые 16 ГБ исторических CSV — те остаются локально для обучения и не идут на прод).

## Первоначальная настройка сервера

```bash
# на самом VPS, от sudo-пользователя
apt update && apt install -y docker.io docker-compose-plugin
usermod -aG docker $USER   # затем перелогиниться
```

## Разворачивание

```bash
git clone <репозиторий> jkh && cd jkh
cp .env.example .env   # заполнить реальные пароли/секреты — не коммитить
export DOMAIN=jkh.example.ru   # домен должен указывать A-записью на IP сервера
docker compose -f docker-compose.yml -f deploy/docker-compose.prod.yml up -d
docker compose exec backend alembic upgrade head
```

Caddy сам получит и обновит сертификат Let's Encrypt по домену `DOMAIN` — вручную
настраивать certbot/nginx не нужно.

## Backup/restore (раздел 12 ТЗ: RTO ≤ 4 часа)

`deploy/backup.sh` — `pg_dump -Fc` из контейнера `db` в `<репозиторий>/backups/jkh_<UTC-время>.dump`
(каталог вне git, см. `.gitignore`), ротация — хранит дампы за последние 14 дней
(`JKH_BACKUP_RETENTION_DAYS`, если нужно другое число). `deploy/restore.sh <дамп>` —
останавливает `backend`/`worker`, `pg_restore --clean --if-exists` поверх текущей БД,
запускает их обратно; интерактивное подтверждение (пропускается, если стоит cron/без tty).

Измерено локально 15 сентября 2026 на минимальном наборе данных (объём на реальном проде
будет больше — 5400 каналов/182 тыс. эпизодов/73 тыс. прогнозов, но это всё ещё десятки МБ,
не сотни ГБ, — сырые CSV на прод не идут, см. раздел «Требования к серверу» выше): backup
0,18 сек, restore <1 сек, сквозной цикл backup → потеря данных → restore → данные на месте
подтверждён на реальном Postgres 16 в docker compose. Даже с многократным запасом на
реальный объём данных и время на SSH/скачивание дампа с сервера — это на порядки быстрее
4-часового норматива.

Cron на VPS (от пользователя с доступом к docker, в каталоге репозитория):

```bash
crontab -e
# 0 3 * * * /opt/jkh/deploy/backup.sh >> /var/log/jkh-backup.log 2>&1
```

**Известное ограничение:** дампы сейчас хранятся на том же сервере, что и сама БД — при
потере диска сервера целиком теряются и данные, и бэкапы (единая точка отказа на уровне
диска, а не только контейнера). Раздел 3 рабочего ТЗ MVP описывает «один сервер», поэтому
это принятое для MVP упрощение, а не проглядели: следующий шаг для прод-контура — синхронизировать
`backups/` на внешнее хранилище (`rclone`/`rsync` на другой сервер или объектное хранилище),
что не сделано намеренно — нет доступа/учётных данных внешнего хранилища на момент написания.

## Ещё не сделано (честно, для матрицы соответствия)

- Резервное копирование `model_versions`/артефактов (файлы `.cbm`, parquet-витрины на
  `worker`) — не настроено; сейчас backup покрывает только БД Postgres.
- Off-site копия бэкапов (см. ограничение выше) — не настроена, нет внешнего хранилища.
- Домен и провайдер VPS ещё не выбраны пользователем на момент написания этого раздела
  (сервер и домен уже подняты позже — см. `docs/documentation/Технические_заметки.md`).
